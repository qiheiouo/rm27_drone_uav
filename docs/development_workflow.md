# 开发流程与工程规范

本文规定 RM_Drone_Nav 的分阶段开发、Git、接口、质量和证据管理方式。它参考 `rm2027_navigation` 中实际存在的 `docs/development_workflow.md`、`docs/research_integration_deployment_principles.md`、`docs/research_asset_and_git_management_principles.md` 和 `docs/repository_workspaces.md`，但已按空中机器人 C99 核心、飞行安全和硬件未定状态重新定义。

## 1. 规范迁移结论

### 1.1 直接沿用的通用原则

- 开发前核对仓库、当前分支、HEAD 和工作区，不覆盖已有修改。
- Research、Integration、Deployment 分离；研究分支是证据载体，不等于可直接合并的产品代码。
- 大改动先定义假设、稳定 baseline、最小可判定实验和 Go / Modify / Stop 标准。
- 公共接口有明确所有者，接口变化必须同步文档和测试。
- 外部代码记录来源、版本/commit、许可证、引入范围、本地修改、替换与回退方法。
- 保留最终结论、关键代码/配置和最小决定性证据，不用测试数量或文档数量代替效果结论。
- 新提交使用简短、准确的中文标题；未经授权不 push、不 merge、不重写历史。
- 不自动清理未知文件，不删除研究证据，不把构建产物或大体积临时数据提交到 Git。

### 1.2 针对无人机调整的原则

哨兵项目的 Research / Integration / Deployment 在本项目中映射为：

```text
Research
  → 软件集成与接口冻结
  → SIL
  → 真实飞控通信或 HIL
  → 无桨台架
  → 系留/受控实机飞行
  → 比赛部署
```

接口所有权由地面车的 TF、topic、Nav2 action 和底盘串口边界，改为：

- `FlightStateProvider`：唯一主飞行状态来源与来源切换；
- `TargetObservationAdapter`：外部视觉观测的坐标、时间和有效性归一化；
- `NavRuntime`：唯一任务级规划、制导和安全决策核心；
- `FlightCommandOwner`：唯一最终导航运动指令生产者；
- 飞控：姿态、角速度、电机、解锁、限幅、外部控制失联和最终急停所有者。

部署准入仍需要飞控、试飞组织和安全员提供人工急停、失联动作、系留方案和逐级放开速度/空间，这些独立机制不是本导航软件要实现的遥控功能。导航软件自身仍必须验证状态有效性、围栏/边界、输出约束、故障响应，以及外部中止输入能停止继续授权运动。

### 1.3 不适用的哨兵专有要求

以下内容不移植：

- Nav2、MPPI、DWB、BehaviorTree.CPP 的具体选型和参数门禁；
- ROS 2 topic/action/launch/runtime profile 的固定命名；
- `map -> odom -> base_link` TF 所有权细则；
- MID360、LIO、二维栅格地图、PCD/PGM 和轮端里程计规则；
- 地面底盘串口运动授权、旧车/新车工作区名称和车辆专用部署步骤。

可以复用其背后的单一数据所有者、默认安全关闭、协议确认后再开真实 IO、仿真不等于实机和分阶段证据原则，但必须使用本项目自己的接口和安全语义。

## 2. 开始任务前

每个任务开始前记录：

1. 当前仓库根目录、分支、HEAD 和远端跟踪关系；
2. 工作区是否有已跟踪或未跟踪修改；
3. 本任务属于文档、Research、Integration、Hardware Validation 还是 Deployment；
4. 允许修改的文件和明确禁止的操作；
5. 需要遵守的权威文档和接口契约；
6. 与风险相匹配的最小验证计划。

发现与任务无关的修改时保留原状。若目标文件已有未知修改且无法安全合并，停止并请求确认。

## 3. 能力与验证状态

文档、提交和汇报必须使用可验证的状态词：

| 状态 | 最低证据 |
|---|---|
| `未实现` | 没有可执行代码或只有设计 |
| `已实现未验证` | 有代码，尚未完成对应测试 |
| `Sim-verified` | 单元、离线回放或软件在环已通过 |
| `Hardware-verified` | 真实设备通信或 HIL/台架已通过，需说明硬件和范围 |
| `Flight-verified` | 受控实机飞行已通过，需说明速度、空间、机体和场景 |
| `Deployable` | 完成比赛配置、回退、现场流程和正式验收 |

禁止把“编译通过”“单元测试通过”“仿真闭环成功”表述为“实机可用”。每个结论同时写清适用平台、输入、版本和未覆盖风险。

设计状态使用：

- `Draft`：内部建议，允许调整；
- `待确认`：依赖外部组、硬件或规则；
- `Frozen`：当前阶段已评审基线，变化需走接口变更流程。

## 4. 分级验证门禁

### L0 静态检查与评审

- 编译器警告、格式和基本静态检查；
- 文档链接、文件路径、符号与源码一致性；
- 代码所有权、单位、坐标、时间和失效语义评审。

### L1 单元与离线数据

- 数学、转换、有效位、边界值、时间戳和状态机测试；
- 真实或合成数据回放；
- 确定性和回归差异检查。

### L2 软件在环

- `NavRuntime` 与动力学/传感器模型闭环；
- 丢帧、延迟、乱序、非有限值和失联注入；
- 验证的是软件组合，不是气动或硬件可靠性。

### L3 飞控通信或硬件在环

- 真实协议、坐标和时间映射；
- 指令有效期、能力协商、重启、队列拥塞和断线；
- 无运动或可控负载优先，保存原始链路和转换后数据。

### L4 受控实机飞行

- 先无桨、再系留低速，再逐步开放范围与速度；
- 人工停桨和现场保护由飞控、试飞组织与安全员独立提供；导航侧同时验证状态有效性、边界约束、故障响应和外部中止输入；
- 任一导航状态不可解释、输入失效或中止失败都判定 Stop/回退。

### L5 比赛部署

- 固定软件/固件/硬件版本和参数；
- 规则复核、验收清单、已知限制、回退包和现场责任人；
- 只允许已通过对应证据的能力进入比赛配置。

## 5. Go / Modify / Stop

每阶段开始前写出通过条件和回退条件。

- `Go`：假设成立，指标和安全门禁满足，可进入下一阶段。
- `Modify`：方向仍合理，但接口、参数或实验需要调整；不得提升能力状态。
- `Stop`：核心假设被否定、风险不可接受、外部条件缺失或收益不足；冻结结论和最小证据。

没有足够数据时默认是 `Modify` 或保持原状态，不用“看起来正常”替代通过标准。

## 6. Git 与工作区

- `main` 保持可理解、可构建和证据边界清楚。
- 功能开发使用隔离分支；高风险探索使用 `experiment/*`，正式收敛使用基于最新主线的干净 `integration/*`。
- 必要时使用 worktree 隔离实验，但 worktree 不是永久归档；移除前确认没有唯一未提交内容。
- 不把失败或冻结研究历史整体合并进主线；只迁移经评审的接口、实现和必要测试。
- 不执行 `push --all`，不为每次审计或中间实验建立永久远端分支。
- 不提交 `build/`、缓存、日志、core dump、大型数据、模型权重和重复 evidence。
- 未经明确授权，不 push、merge、rebase、force push、删除分支或清理未知文件。

提交前：

1. 复核 diff 只包含任务范围；
2. 运行与风险匹配的检查；
3. 更新受影响的文档和测试；
4. 使用一行、简短中文提交说明，例如 `文档：更新平台无关接口规划`。

## 7. 接口与所有权

### 7.1 唯一主状态

任一时刻只允许一个 `FlightStateProvider` 向导航核心提供主位置、速度、姿态和时间。当前实现必须通过 `NavRuntimeConfig.flight_state_source` 在启动时静态选择内部估计链或外部 `FlightState`；运行中不自动切换。外部模式下融合状态直接成为 `NavState`，不得再送入惯性积分器；原始 IMU 只作为碰撞检测等独立测量，不构成第二主状态。未来备用来源只有在显式状态机记录来源、时间、跳变和切换原因后才能加入。

### 7.2 目标观测

视觉组拥有识别与原始输出；导航适配层拥有外参、坐标变换、时间/单位归一化和有效性检查；导航核心拥有跟踪、预测、制导与目标丢失行为。外部已经提供三维结果时不得再次按目标尺寸重建。

### 7.3 最终运动命令

`NavRuntime` 是任务级运动意图的唯一生产者，平台适配器只允许：

- 选择飞控明确支持的控制模式；
- 转换坐标、单位、时间和协议；
- 应用更严格的安全禁用；
- 在过期、失联或无授权时拒绝发送运动命令。

平台适配器不得再运行另一套任务级制导，也不得与 `NavRuntime` 同时输出最终速度。飞控始终拥有低层稳定、限幅、解锁和失联动作。

当前第一阶段约束：`CtrlOutput.velocity_cmd` 是导航期望速度；正式 `NavApp` 链路只有
`FcuMotionAuthorization` 可以把它转换成 `motion_enabled=1` 的 `FcuSetpoint`。定位或必需输入
失效、任务非运动状态、命令非法和发送失败都必须撤销授权；恢复后必须观察新的低→高授权边沿，
不得把定位恢复等同于运动恢复。`nav_fcu_set_motion_authorized()` 只传递主机授权状态，不能命名或
记录为飞控实际 armed/接受/执行。禁用包、零速度、停止发送和超时在真实飞控上的动作仍需按所选
协议完成 HIL/台架验证。

### 7.4 契约变更

任何公共接口变更必须同时更新：

- 字段、单位、坐标系、时间基准和有效位说明；
- 唯一所有者和调用方向；
- 兼容/版本策略；
- 过期、乱序、非有限值、失联和恢复行为；
- 单元、回放或集成测试；
- `docs/architecture.md` 和相关平台文档。

## 8. C99、C++ 与平台依赖

- `core/`、可复用 `perception/` 和协议无关 `flight/` 继续使用 C99 与固定宽度类型。
- 核心不依赖 HAL、POSIX、线程、文件系统、ROS 2、Docker 或具体 SDK。
- 不因候选 ARM Linux 平台而整体迁移 C++。
- 新 C++17/20 只用于 Linux 设备/协议 SDK、线程/IPC、进程生命周期或复杂资源管理，并通过 `extern "C"`、固定大小 POD、显式缓冲区与错误码连接 C 核心。
- 不跨 ABI 暴露 STL 容器、异常、RTTI 对象或隐式所有权。
- MCU 适配层避免动态分配和阻塞 IO；Linux 适配层即使可用动态资源，也不得改变核心确定性语义。

## 9. 外部代码与依赖

任何外部库、协议实现、飞控驱动或参考算法进入仓库前，至少记录：

- 来源 URL、版本、branch/commit；
- 许可证和再分发条件；
- 精确引入范围与本地修改；
- 为什么需要、替代方案和移除方法；
- 位于哪个平台边界，是否影响核心；
- 对应的构建、测试、硬件和安全证据。

优先通过小型适配器或明确子模块集成，不直接把整个外部工程复制进主线。

## 10. 文档与证据

- README 只描述当前入口、能力状态和权威索引。
- `General_Plan.md` 维护任务边界、决策状态和阶段路线。
- `docs/architecture.md` 维护实际代码证据、公共契约和平台边界。
- 专题文档只负责其模块，候选方案必须在开头标记状态。
- 研究结束保留一份高质量结论、关键代码/配置和最小决定性证据；不保存全部中间产物。
- 文档任务不强制运行全量仿真；只做链接、路径、符号、状态表述和 diff 检查即可。代码或接口变化再按风险增加测试。

本规范不授权自动 push、merge、硬件运动测试或破坏性 Git 操作。
