# RM_Drone_Nav 系统工作原理与项目讲解指南

这份文档有两个用途：

1. 帮助项目成员理解代码如何组成一条完整的自主导航闭环；
2. 帮助你向有开发基础的人介绍项目，并准确说明已经完成什么、还缺什么。

建议第一次阅读按顺序看第 1～9 节。准备交流时，直接使用第 12～16 节。

快速导航：

## 1. 先用一句话定义系统

> RM_Drone_Nav 是一套面向 RoboMaster 微型无人机、按 STM32 级资源约束设计的任务级自主导航原型：它接收 IMU、光流、测距和视觉目标等观测，完成状态估计、任务决策、轨迹与制导、安全降级，再把有时效的运动目标交给独立飞控执行。

这里最重要的词是“任务级导航”，不是“从电机开始重新写一套飞控”。

系统负责回答：

- 我现在在哪里、运动状态是否可信？
- 当前任务阶段是什么？
- 应该向哪里飞、以什么速度接近？
- 目标或基座丢失后怎么办？
- 撞击后怎样稳定、恢复定位并返航？
- 轨迹、传感器、通信或控制异常时怎样降级？

独立飞控负责回答：

- 如何稳定姿态和角速度？
- 如何把速度或加速度目标转换为姿态、推力和电机输出？
- 导航通信失联后如何刹停、悬停或受控降落？
- 什么时候允许解锁，什么时候必须急停？

## 2. 为什么采用这种架构

任务包含起飞、搜索、目标接近、受控接触、撞击恢复、返航和视觉停靠。困难不只在“飞到目标”，而在于接触后可能同时发生：

- 瞬时大加速度和大角速度；
- 图像模糊或视觉中断；
- 惯性状态突变；
- 估计器退化甚至丢失；
- 剩余任务时间不足；
- 返航和精确停靠仍然必须完成。

因此，系统不是单一算法，而是一组有明确边界和降级路径的模块。设计原则是：

1. **飞行稳定与任务导航分层。** 姿态环和电机环不依赖导航任务是否正常运行。
2. **固定资源。** 核心代码使用 C99、固定容量数组和有界循环，不依赖动态内存。
3. **先保证闭环，再增加高级算法。** 简单且可验证的制导始终作为后备路径。
4. **异常是正常输入的一部分。** 丢帧、时间戳异常、非有限值、撞击和链路中断都有明确处理。
5. **主机与嵌入式复用同一算法入口。** 仿真和 STM32 都调用 `NavRuntime`，避免维护两份任务逻辑。

## 3. 整体架构

推荐按“两块 MCU + 两条闭环”理解当前系统：

```text
                         ┌──────────── 飞控 MCU ────────────┐
IMU / 光流 / ToF ───────→│ 采样、飞控估计、姿态/角速度环、混控 │
                         └───────────┬───────────────↑──────┘
                                     │ FCU 状态       │ 有时效运动目标
                                     │ UART           │ UART
                         ┌───────────↓───────────────┴──────┐
目标/基座相机 ──────────→│             导航 MCU              │
局部障碍/任务命令 ──────→│ 感知 → 估计 → FSM → 安全 → 制导/规划 │
                         └──────────────────────────────────┘
```

如果最终选定的飞控已经融合 IMU、光流和测距，导航 MCU 可以优先消费飞控输出的位置、速度和姿态，同时保留原始 IMU 用于撞击检测。目标识别和基座识别仍可由导航侧完成。

主机仿真使用另一条输入路径，但算法核心相同：

```text
仿真动力学 → 仿真传感器 → NavRuntime → 控制输出 → 仿真动力学
                                ↓
                         日志、遥测、场景断言
```

所以主机仿真不是另写的一套“演示代码”，而是给真实算法调用链提供可重复输入。

## 4. 三个不同时间尺度的闭环

讲解时最好画出这三层，否则别人容易误以为所有控制都通过 UART 完成。

| 层次 | 典型职责 | 建议起始频率 | 所在位置 |
|---|---|---:|---|
| 飞行稳定环 | IMU 采样、角速度、姿态、混控、电机 | ≥500 Hz | 飞控 MCU |
| 导航运动环 | 状态更新、局部规划、制导、速度/加速度目标 | 100～200 Hz | 导航 MCU |
| 任务决策环 | 搜索、目标确认、撞击恢复、返航、停靠 | 由事件和计时器推进 | `MissionFsm` |

这些数字只是软件设计起点，不是实机测试结论。最终必须测量：

- 传感器采样到导航可见的延迟；
- 导航计算最坏执行时间；
- UART 传输和队列抖动；
- 飞控收到目标到实际响应的延迟；
- 对应飞行速度下的制动距离和稳定裕量。

## 5. 一次 `NavRuntime` 周期发生了什么

系统的中心入口是 [`nav_runtime_step`](../core/runtime/nav_runtime.c)。理解下面的顺序，就理解了大部分系统。

```text
输入与时间戳检查
    ↓
状态估计 / 光流里程计
    ↓
撞击检测、目标跟踪、基座跟踪
    ↓
绝对基座重定位与撞击恢复更新
    ↓
局部障碍和多机冲突预测
    ↓
SafetyMonitor 计算安全等级和覆盖请求
    ↓
MissionFsm 决定任务状态与制导模式
    ↓
轨迹规划或对应制导器生成 GuidanceOutput
    ↓
局部避障 / 多机避让修正
    ↓
位置速度控制器生成 CtrlOutput
    ↓
输出状态、事件日志和遥测快照
```

### 5.1 输入健康检查

`NavRuntimeInput` 可以携带 IMU、光流、里程计、目标像素、基座像素、障碍、他机状态和任务命令。运行时检查：

- 必需输入是否存在；
- 数值是否有限；
- 时间戳是否过期、重复、倒序或异常超前；
- 导航调用周期是否出现连续超时。

IMU 是必需输入。必需输入不可信时，本周期输出被标记为无效并清除解锁；可选输入失效时，系统丢弃该通道并尝试降级继续。

### 5.2 状态估计

[`StateEstimator`](../core/state_estimator/state_estimator.h)维护位置、速度、姿态、角速度、线加速度、质量和健康状态：

```text
INIT → IMU_ONLY → VISUAL_AIDED / TRACKING
                    ↓
                 DEGRADED → LOST
                    ↑         ↓
             RELOCALIZED ← RECOVERING
```

当前实现组合：

- IMU 惯性预测和倾斜修正；
- 光流视觉里程计的水平位置/速度校正；
- ToF 高度校正；
- 基座视觉观测提供绝对位置重定位；
- 创新门限阻止异常观测直接拉飞估计器。

`TRUTH` 模式只用于仿真对照，不是实机运行方案。

### 5.3 目标与基座感知

当前代码从“像素观测”开始，不负责真实图像中的目标分类和 marker 解码。

- [`TargetTracker`](../perception/target_tracker/target_tracker.h)使用固定状态 alpha-beta 跟踪器输出相对位置、速度、方位、置信度和观测年龄。
- [`HomeDetector`](../perception/home_detector/home_detector.h)滤波基座相对位置和偏航，用于重定位、精细归航和停靠。
- [`VisionFrontend`](../perception/vision_frontend/vision_frontend.h)根据下视特征、陀螺和高度估计光流里程计。

目标或基座暂时丢失时，不会立刻把旧观测永久当真，而是经过短时预测、重捕获、重新搜索或受限盲降路径处理。

### 5.4 撞击检测与恢复

撞击检测融合：

- 加速度尖峰；
- 角速度尖峰；
- 速度跳变；
- 姿态跳变。

检测器只在相关任务阶段布防，并带连续样本确认、置信度、不应期和上升沿事件，避免普通机动反复触发。

确认撞击后的恢复不是一个简单的“暂停”，而是有界状态机：

```text
VISUAL_HOLD
  → ATTITUDE_RECOVERY
  → VELOCITY_DAMPING
  → ESTIMATOR_CHECK
  → BREAKAWAY
  → COMPLETE
```

如果估计器无法恢复或恢复超时，则转入安全降落。硬时间截止、围栏和人工急停在恢复期间仍然有效。

### 5.5 任务状态机

[`MissionFsm`](../core/mission/mission_fsm.h)管理完整任务生命周期：

```text
BOOT → SELF_CHECK → DOCKED → TAKEOFF → OUTBOUND → SEARCH
  → TARGET_ACQUIRE → TARGET_TRACK → TERMINAL → IMPACT
  → RECOVERY → BREAKAWAY → RETURN_HOME → HOME_SEARCH
  → HOMING → DOCKING → DOCKED
```

异常分支：

```text
ESTIMATOR_LOST → 恢复原任务或 EMERGENCY_LAND
EMERGENCY_STABILIZE → EMERGENCY_LAND
```

状态机本身不直接计算控制量。它只决定：

- 当前任务状态；
- 使用哪种制导模式；
- 当前航点或保持点；
- 是否完成、失败、返航或紧急降落。

这使“任务为什么转移”和“飞机怎样运动”保持分离。

### 5.6 轨迹、制导和控制

系统不是所有时候都使用同一种算法：

| 场景 | 输出方式 |
|---|---|
| 起飞、保持、降落 | 专用简单制导 |
| 出航、搜索、返航 | 航点队列和固定容量五次多项式轨迹 |
| 目标末端接近 | `PURSUIT/CLOSING/FINAL_ALIGN/CONTACT_APPROACH/REACQUIRE` 分阶段制导 |
| 撞击恢复 | 恢复状态机生成保持、阻尼和脱离目标 |
| 基座归航 | 基座相对观测视觉伺服 |
| 轨迹生成失败 | 时间拉伸、局部绕行或简单限速航点制导 |

`GuidanceOutput` 表示位置、速度、加速度和偏航目标；`CtrlOutput` 是当前主机模型使用的期望加速度和偏航角速度。双 MCU 实机路径再把二者包装成 `FcuSetpoint`，由具体飞控适配器选择它真正支持的速度或加速度接口。

### 5.7 安全覆盖

[`SafetyMonitor`](../core/safety/safety_monitor.h)不直接改任务状态，而是输出安全等级、原因位和请求：

```text
SAFE
DEGRADED
RETURN_REQUIRED
RECOVERY_REQUIRED
EMERGENCY
```

主要原因包括软/硬任务截止时间、围栏、估计器质量、撞击、碰撞、轨迹失效和持续控制饱和。

可按以下优先级理解：

```text
硬截止/围栏/持续严重碰撞/估计器 LOST/持续控制饱和
    > 撞击恢复
    > 返航请求
    > 普通任务
```

瞬时风险一般先进入降级或计时，而不是一个采样就紧急降落；但非有限必需输入和结构性错误会立即拒绝输出。

## 6. 主要模块怎样协作

| 模块 | 主要输入 | 主要输出 | 解决的问题 |
|---|---|---|---|
| `NavRuntime` | 全部归一化输入 | 完整导航输出 | 保证统一调用顺序和平台复用 |
| `StateEstimator` | IMU、里程计、ToF | `NavState` | 当前运动状态和可信度 |
| `VisionFrontend` | 特征、陀螺、高度 | `OdomSample` | 轻量光流里程计 |
| `TargetTracker` | 目标相对观测 | `TargetTrack` | 目标短时预测和重捕获 |
| `HomeDetector` | 基座相对观测 | `HomeTrack` | 重定位、归航和停靠依据 |
| `ImpactDetector` | IMU、速度、姿态 | `ImpactReport` | 区分接触事件与普通运动 |
| `ImpactRecovery` | 导航状态和里程计健康 | 恢复制导 | 撞击后稳定和有界恢复 |
| `MissionFsm` | 状态、感知、安全请求 | 任务状态和制导模式 | 管理完整任务生命周期 |
| `TrajectoryPlanner` | 起终点、约束、障碍 | 固定段轨迹和检查报告 | 生成可验证的平滑运动 |
| `SafetyMonitor` | 导航质量、风险、时间 | 安全等级和覆盖请求 | 统一异常优先级 |
| `PosController` | 制导目标、导航状态 | 加速度和偏航角速度 | 主机闭环与自定义低层接口 |
| `FcuBridge` | FCU 状态和导航目标 | 有时效 FCU 指令 | 隔离具体飞控协议和断线风险 |
| 诊断/遥测 | 运行时输出和事件 | 环形日志、二进制帧 | 重现和定位故障 |
| Swarm 接口 | 他机状态/未来轨迹 | 冲突报告和避让偏置 | 可选的多机扩展 |

## 7. 双 MCU 和 UART 具体怎样接

这一层的详细契约见[双 MCU 飞控 UART 桥接](fcu_uart_bridge.md)。讲解时抓住四点即可。

### 7.1 飞控发给导航

推荐包含：

- 采样时间戳和序号；
- 姿态四元数、角速度和线加速度；
- 本地位置、速度和高度；
- 估计器健康、解锁、外部控制模式；
- 电池状态；
- 飞控支持的位置/速度/加速度/偏航能力。

飞控状态超过配置时间未更新时，导航桥进入 `STALE`，停止生成运动指令。

### 7.2 导航发给飞控

`FcuSetpoint` 带：

- 序号和生成时间；
- `motion_enabled`；
- 有效字段掩码；
- 位置、速度、加速度候选目标；
- 偏航或偏航角速度；
- 指令有效期。

适配器必须只选择飞控明确支持的控制量，不能同时重复闭合速度环和加速度环。

### 7.3 为什么必须有有效期

如果 UART 中断而飞控永久执行最后一条 `1 m/s` 速度指令，任何导航侧安全逻辑都失去意义。因此：

- 导航状态过期后停止发送运动目标；
- 每条指令自身带有效期；
- 飞控还必须有独立的 Offboard/Guided 失联保护；
- 失联动作由飞控最终执行，不能依靠已经失联的导航 MCU。

### 7.4 当前还没有做什么

因为飞控尚未选型，当前没有绑定 MAVLink、某款固件消息或具体 STM32 UART HAL。已有的是协议无关契约、参考 `RMFC` 字节流、固定内存解析器和断线仿真。选型后增加适配器，而不是重写导航核心。

## 8. 可选的集群能力

当前 `main` 已经合入最多 4 架他机的状态、固定链路帧、确定性多机网络仿真和冲突邻机失联保护。下面三条分支是这些提交的来源和历史开发边界，仍保留在远端用于追溯：

| 分支 | 能力 | 关系 |
|---|---|---|
| `feat/swarm-link-protocol` | 固定长度状态帧、CRC、序号和邻机超时表 | 已合入 `main` |
| `feat/swarm-network-simulation` | 多个独立 `NavRuntime` 和确定性故障网络 | 已合入 `main` |
| `feat/swarm-link-loss-guard` | 冲突邻机失联后的保持与恢复确认 | 已合入 `main` |

这仍然不是完整编队、任务分配或分布式轨迹优化器。当前任务如果最终采用多机串行出动，集群模块可以保持关闭。

讲解时仍要区分“架构预留”“历史开发分支”和“已经合并到主线”三种状态；当前集群三层能力已经在 `main`，但这不等于完成完整编队或分布式优化。

## 9. 软件验证体系证明了什么

验证分为五层：

1. **模块测试**：数学、相机、估计器、跟踪、轨迹、安全、FCU 桥等边界条件；
2. **闭环场景**：从起飞到接触、恢复、返航和停靠；
3. **故障注入**：丢帧、冻结、延迟、非有限值、时间戳和调度异常；
4. **确定性回放和遥测**：保存输入或输出，检查同一数据得到同一结果；
5. **质量门禁**：警告即错误构建、全部 CTest、空白错误、绝对路径和构建产物检查。

当前分支可执行：

```powershell
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
cmake -DQUALITY_BUILD_DIR=build -DQUALITY_CONFIG=Debug -P cmake/quality_gate.cmake
```

这些验证可以说明：

- 软件状态机和模块组合在声明场景中可重复；
- 异常分支确实触发，不只是最后打印成功；
- 非有限值、过期输入和链路中断不会静默沿用旧控制；
- 固定内存边界和主要降级路径有回归保护。

它们不能说明：

- 实机一定稳定；
- 相机在真实光照和运动模糊下能可靠识别；
- UART、电机、电池和机体延迟已经满足要求；
- 参数可以不经标定直接上机；
- 系统已经复现论文实验性能。

## 10. 推荐的代码阅读顺序

给开发者介绍时，不建议从某个滤波公式或 1000 行主循环开始。按下面顺序更容易建立整体认识。

1. [`README.md`](../README.md)：项目边界、构建方法和已知限制；
2. [`nav_runtime.h`](../core/runtime/nav_runtime.h)：完整输入、输出、配置和持久状态；
3. [`nav_runtime_step`](../core/runtime/nav_runtime.c)：一次导航周期的真实调用顺序；
4. [`mission_fsm.h`](../core/mission/mission_fsm.h)和 [`mission_fsm.c`](../core/mission/mission_fsm.c)：任务生命周期；
5. [`safety_monitor.c`](../core/safety/safety_monitor.c)：异常优先级；
6. [`impact_recovery.c`](../core/safety/impact_recovery.c)：项目最特殊的接触后恢复；
7. [`trajectory_planner.c`](../core/planner/trajectory_planner.c)和 [`guidance.c`](../core/guidance/guidance.c)：正常运动如何生成；
8. [`platform/host/main.c`](../platform/host/main.c)：仿真怎样构造输入并断言分支；

1. 输入是什么，坐标系和单位是什么？
2. 哪些状态跨周期保存？
3. 什么条件算成功、退化和失败？
4. 失败后谁接管，输出是否仍有界？

### 可以直接使用的开场白

> 这个项目不是重写飞控，而是在飞控之上做一层任务级自主导航。它针对微型无人机的短时任务，把起飞、搜索、目标接近、受控接触、撞击恢复、返航和视觉停靠串成一个闭环。导航核心按 STM32 级资源设计，主机仿真和嵌入式使用同一个 `NavRuntime`。目前软件状态机、故障注入、日志回放和双 MCU 失联保护已经跑通，但真实视觉、具体飞控适配、参数标定和实机稳定性仍需要硬件验证。

这段话大约一分钟，并且不会过度承诺。

### 13.1 五分钟版本

## 14. 推荐现场演示

先完成一次构建，然后选择 2～3 个场景。演示太多会掩盖重点。

### 演示一：完整正常任务

```powershell
.\build\mission_sim.exe
```

指出状态如何从起飞推进到目标、撞击恢复、返航和停靠，并解释 `MISSION_SUCCESS` 只是软件闭环结果。

### 演示二：感知或估计异常

```powershell
.\build\mission_sim.exe --scenario target-loss
.\build\mission_sim.exe --scenario impact-lost
```

指出系统不是一路假设观测永远存在，而是实际进入重捕获、恢复或安全分支。

### 演示三：输入安全拒绝

```powershell
.\build\mission_sim.exe --scenario imu-stale
```

这里的通过标准不是完成任务，而是检测到必需输入过期、拒绝继续输出并留下诊断证据。

### 演示四：双 MCU 断线

```powershell
.\build\fcu_bridge_sim.exe
```

重点看三条事件：

```text
FCU state stale; navigation output inhibited
FCU command expired; receiver failsafe active
FCU state link recovered
```

这能直观说明为什么“有 CRC”还不够，还必须有双向超时和指令有效期。

## 15. 常见追问及建议回答

### “为什么不用同一块 MCU？”

可以使用同一块，但如果不修改开源飞控，把导航放在独立 MCU 更容易保持控制边界。飞控继续负责硬实时稳定，导航通过标准外部控制接口给速度或加速度目标。UART 不是姿态环的一部分，因此它要求低延迟和可预测，但不承担最高频硬实时闭环。

### “为什么导航和飞控可能都有估计器？”

当前核心保留独立估计能力，方便主机验证和不同硬件方案。选型后应明确单一主要状态来源：如果飞控已经可靠融合光流和测距，导航优先消费飞控融合状态；导航自己的相对目标和基座重定位仍可服务任务层。不能让两套坐标系未经定义就混用。

### “导航最后到底发速度还是加速度？”

内部同时保留 `GuidanceOutput` 和 `CtrlOutput`。外部飞控适配器优先选择飞控原生支持的速度接口；只有明确支持外部加速度目标时才使用加速度。不能同时让导航和飞控重复实现同一个速度环。

### “为什么一定要状态机？”

因为任务阶段具有不同的传感器可信度、目标和失败策略。搜索时丢失目标很正常，接触阶段的撞击是预期事件，而返航阶段的同样加速度尖峰可能是故障。状态机让事件含义和恢复路径显式可测。

### “为什么不直接移植论文代码？”

论文系统往往依赖高算力平台、完整 VIO、地图和非线性优化。当前项目只吸收固定维度轨迹、时效检查、相对观测和共享未来状态等思想，再按任务和 MCU 资源重新设计。目标是可落地的最小闭环，不是缩小版论文计算栈。

### “测试都通过是不是就能飞？”

不能。测试证明软件在模型和声明故障下行为一致，不证明空气动力、传感器噪声、机体碰撞、无线链路和实际控制裕量。上机前仍需 SIL、HIL、无桨台架、系留低速和逐级开放。

### “集群系统完成了吗？”

主线已经具备通信、确定性网络仿真和冲突邻机失联保护，但不是完整编队或分布式优化；是否需要继续取决于比赛是否真的允许或需要多机同时飞行。

### “最担心的技术风险是什么？”

当前最大的未知不是代码能否编译，而是实际飞控接口、相机能力、撞击时 IMU/视觉表现、端到端延迟、机体接触结构和剩余电量。它们需要选型和实测数据才能收敛。

## 16. 请开发者重点评审什么

向比你有经验的人介绍时，不只是“展示成果”，还应明确请求他们帮助评审：

1. **飞控选型与外部控制接口**：是否原生支持速度目标、状态输出和失联保护；
2. **控制权边界**：速度环究竟放在哪一侧，是否存在重复闭环；
3. **坐标和时间**：NED/ENU、机体系、四元数顺序、采样时间与接收时间；
4. **UART 预算**：消息频率、峰值带宽、DMA 队列和最坏延迟；
5. **状态估计架构**：飞控融合状态与导航相对感知怎样组合；
6. **安全动作**：断线、估计器丢失、低电量、围栏和急停由谁最终执行；
7. **硬件资源**：目标 MCU 的 RAM、Flash、FPU、栈和最坏执行时间；
8. **验证路线**：哪些场景先 SIL/HIL，哪些必须无桨或系留测试；
9. **比赛约束**：30 秒预算、多机规则、无线通信和停靠/充电规则是否准确。

可以这样结束介绍：

> 软件层现在已经有完整调用链、异常分支和回归框架。我最希望你帮我确认的是飞控接口与控制权边界、坐标和时间约定，以及哪些软件假设必须尽快用实物数据推翻或标定。

这比笼统地问“你觉得代码怎么样”更容易得到有价值的反馈。

## 17. 表述边界：哪些话可以说，哪些不能说

| 可以明确说 | 需要附带条件 | 现在不能说 |
|---|---|---|
| 核心是 C99 固定内存设计 | 目标 MCU 资源是否足够要实测 | 已经在 STM32 上满足实时性 |
| 主机与 STM32 骨架共用 `NavRuntime` | 板级 HAL 和飞控适配尚未完成 | 已经是可直接烧录飞行的固件 |
| 闭环场景和故障回归可重复 | 只覆盖模型和声明故障 | 已证明实机安全可靠 |
| 有撞击检测和分阶段恢复 | 阈值必须按机体标定 | 撞击后一定能恢复 |
| 有双 MCU 协议无关桥接 | 尚未绑定具体飞控 | 已兼容所有开源飞控 |
| 有集群扩展分支 | 不是完整编队系统 | 已实现论文级集群导航 |

## 18. 术语速查

| 术语 | 在本项目中的含义 |
|---|---|
| FCU | 飞行控制器，负责低层稳定和电机控制 |
| MCU | 微控制器；导航和飞控可以分别使用一颗 |
| FSM | 有限状态机，用显式状态和转移组织任务 |
| Guidance | 制导目标，如位置、速度、加速度和偏航 |
| Setpoint | 交给下一控制层执行的目标值 |
| Estimator | 融合传感器并输出位置、速度、姿态和健康度 |
| VO | Visual Odometry，视觉里程计 |
| ToF | Time of Flight，飞行时间测距，主要用于高度 |
| Watchdog | 检测任务调用超时并触发安全处理的看门狗 |
| CRC | 检测传输损坏的循环冗余校验，不等于身份认证 |
| SIL | Software-in-the-loop，软件在环 |
| HIL | Hardware-in-the-loop，硬件在环 |
| Offboard/Guided | 飞控接受外部运动目标的控制模式 |
| Relocalization | 利用基座等绝对参考重新对齐导航坐标 |

## 19. 最后再压缩成三句话

1. 这是一套在独立飞控之上的任务级导航系统，不直接控制电机。
2. 它的核心价值是把感知、估计、任务、撞击恢复、返航、停靠和安全降级组成同一条可回归闭环。
3. 软件骨架已经足够进入飞控选型、协议适配和分级硬件验证阶段，但还不能把主机仿真结果当成实机结论。
